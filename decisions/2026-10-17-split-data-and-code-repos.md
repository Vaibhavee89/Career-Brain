## Context

This repo holds both the Career Brain tooling (`src/`, `tests/`, CI, `pyproject.toml`) and the brain's content (`profile/`, `projects/`, `decisions/`, `experience/`, `wins.md`, `job-search/`, `inbox/`). Privacy relies on a `public` flag per page, and the review on this date found employer-internal sample pages marked `public: true`.

The content is already on the remote. `origin/main` contains `profile/about.md`, `experience/sample-blinkit-data-platform.md`, `projects/sample-etl-helper-agent.md`, and `projects/sample-mcp-connectors.md`. A `.gitignore` entry cannot remove files that are already tracked or already pushed.

## Options considered

- Keep one repo and add private folders to `.gitignore`. Cheap, but the existing history keeps the content, a stray `git add -f` still publishes it, and privacy depends on the flag alone.
- Private data repo plus public code repo. The code repo never holds personal content, so leakage needs a structural mistake rather than a flag mistake. Costs a second repo to sync.
- Public code repo with the content published only through a generated site (phase 4). Still needs the data somewhere, so it reduces to one of the options above.

## Decision

Split into two repos:

- `careerbrain` (public): `src/`, `tests/`, `.github/`, `pyproject.toml`, `brain.config.yaml`, `Readme.md`, `LICENSE`, and the `_template.md` files with no personal content.
- `careerbrain-data` (private): every page under `profile/`, `projects/`, `decisions/`, `experience/`, `learning/`, `job-search/`, `inbox/`, and `wins.md`.

The tooling points at the data repo through `CAREERBRAIN_ROOT` or `--root`, which `bootstrap.py` already supports, so the split needs no code change.

The public repo should start from a fresh history, not a rewrite of this one. Rewriting or force-pushing the existing remote history is destructive and needs explicit approval first.

## Why

- Git keeps history, so only a split that starts a clean public history keeps the personal content out of what gets published.
- The public-only filter in `core/retrieval.py` stays as a second layer of defense. It is no longer the only one.
- Phase 4's public site can be generated by copying `public: true` pages from the private data repo into a build step, so the public site never needs the private repo's history.
